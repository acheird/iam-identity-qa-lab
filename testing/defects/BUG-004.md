# BUG-004 — Joiner log shows computed username instead of actual username for existing employees

- **Severity:** Low
- **Priority:** Low
- **Requirement:** None directly — this is a logging/output accuracy
  issue, not an access or identity defect. Related to the same
  "output must reflect actual state" principle behind BUG-003.
- **Environment:** `provision-users.ps1`, discovered after the
  BUG-001/ADR-0007 username-generation fix.

## Preconditions

An employee already exists in Keycloak with a username that predates
the ADR-0007 change (e.g. `maria`, created before the fix, under the
old `FirstName`-only scheme).

## Steps to Reproduce

1. Run `.\scripts\provision-users.ps1` against any employee who
   already exists in Keycloak with a pre-ADR-0007 username.

## Expected Result

The "FOUND in Keycloak" log line should display the employee's
**actual** Keycloak username.

## Actual Result

The log line displays the **newly computed** username (per the
current `FirstName-EmployeeID` formula), not the actual one stored in
Keycloak — even when they differ.

```
E001 (maria-e001): FOUND in Keycloak (id: d1d59f00-...)
```

Actual Keycloak username (Admin Console → Users → maria → Details →
Username field): `maria`.

## Root Cause / Suspected Cause

`$username` is computed once per employee, from the CSV, before the
Keycloak lookup — and the same variable is used in both the "FOUND"
and "NOT FOUND - creating" log lines. For the "FOUND" branch, the
script already has the real username available on `$existingUser`
(the Keycloak API response), but never reads it — it logs the
computed value regardless.

## Impact

Cosmetic/log-accuracy only — no identity, group, role, or access
state is affected; `$existingUser.id` (used for all subsequent
group/role operations) is correct throughout. The impact is purely
that the execution log misrepresents an existing employee's real
username, which could mislead anyone reading the log or an audit
trail.

## Status

**Closed.**

**Resolution:** Fixed — the "FOUND" branch now logs
`$existingUser.username` (the real Keycloak value) instead of the
locally computed one. Retested against the full employee set: legacy
usernames (`maria`, `nikos`, `giorgos`, `eleni`, `alex`, `leaver`)
now display correctly as their actual values, while employees
created after ADR-0007 (`test-e006`, `test-e007`) correctly show the
new scheme — confirming both branches log accurately.

## Fix Design (decided, pending implementation)

This is grounded in an explicit decision, not just a patch: existing
usernames are **never** retroactively renamed (ADR-0007 addendum) —
old- and new-scheme usernames legitimately coexist. Given that, the
log output must reflect **actual** state, not the newly computed
formula, for any employee already found in Keycloak.

**Fix:** in the "FOUND" branch, log `$existingUser.username` (already
available on the Keycloak API response) instead of the locally
computed `$username`. The computed `$username` remains correct and
unchanged for the "NOT FOUND - creating" branch, where it **is** the
real, new username about to be assigned.
