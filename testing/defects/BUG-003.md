# BUG-003 — Role reconciliation reports "already correct" when employee role is actually missing

- **Severity:** High
- **Priority:** Medium
- **Requirement:** REQ-009 (Role Change), whose reconciliation logic
  produces the false report.
- **Environment:** Keycloak 26.7.3 (Docker), `update-users.ps1`,
  executed via `acme-provisioner`.

## Preconditions

An employee (`E004`, Eleni) currently holds **no** business roles at
all (both `employee` and `manager` are absent — in this case, because
`deprovision-users.ps1` had removed `employee` earlier). CSV
`Role=Employee`.

## Steps to Reproduce

1. Ensure an employee has no business roles assigned in Keycloak, but
   the CSV still says `Role=Employee`.
2. Run `.\scripts\update-users.ps1`.

## Expected Result

The role reconciliation should detect that `employee` is required by
the CSV but missing in Keycloak, and either add it or, at minimum,
not report the state as already correct.

## Actual Result

Output reports `E004: role already correct (employee)`, while the
employee actually has **no** business role at all.

```
E004: role already correct (employee)
```

Actual Keycloak state (Role mapping tab):
```
default-roles-acme   (no "employee")
```

## Root Cause / Suspected Cause

The role reconciliation logic in `update-users.ps1` only checks the
`manager` dimension (`$hasManager` vs `$shouldBeManager`); it never
asserts that `employee` itself is present when `$shouldBeManager` is
`false`. Any code path that falls through to the `else` branch is
reported as "already correct" without verifying `employee`
specifically — this is a gap in the reconciliation logic itself, not
specific to the termination scenario that happened to reveal it.

## Impact

This produces a false positive in the automation's own output — the
script reports a state as correct when the actual IAM state does not
match what the CSV requires. This undermines trust in the Mover's
self-reported status and could mask a real access-integrity problem
in any scenario where `employee` is missing for a reason unrelated to
termination (e.g. a future defect elsewhere).

## Status

Open — fix design decided, not yet implemented (see below).

## Fix Design (decided, pending implementation)

**Decision:** role reconciliation must compare the **full** desired
role set against the full current role set — not just check whether
`manager` is present or absent.

```
CSV Role   →  Desired business roles
Employee   →  { employee }
Manager    →  { employee, manager }
```

The script then reconciles toward this desired set: add whatever is
missing, remove whatever is present but not desired. This replaces
the current logic, which only asks "does `manager` match?" and
silently assumes `employee` is fine — the gap BUG-003 exposed.
Example this fixes: CSV says `Employee`, but the employee currently
has neither `employee` nor `manager` (e.g. because Leaver removed
`employee` earlier) — the fix must add `employee`, not report
"already correct".
