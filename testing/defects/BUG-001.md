# BUG-001 — Username collision prevents provisioning of employees with duplicate first names

- **Severity:** High
- **Priority:** Medium
- **Requirement:** REQ-007 (Joiner Provisioning) — primary. Related:
  REQ-002 (identity uniqueness is correctly anchored to `EmployeeID`
  elsewhere; this defect is a separate, unaddressed uniqueness
  concern in username generation specifically).
- **Environment:** Keycloak 26.7.3 (Docker), `provision-users.ps1`,
  executed via `acme-provisioner`.

## Preconditions

An employee already exists in Keycloak with `FirstName=Test`
(`E006`, username `test`, created via a prior, successful Joiner run
— see `testing/test-cases.md` TC-001).

## Steps to Reproduce

1. Add a new row to `data/employees.csv` for a different
   `EmployeeID`, with the **same** `FirstName` as an already-existing
   employee — e.g. `E007,Test,Manager,Finance,Manager,Active,...`.
2. Run `.\scripts\provision-users.ps1`.

## Expected Result

Both employees are provisioned as independent identities, regardless
of sharing the same first name — `EmployeeID` is the uniqueness
anchor (REQ-002), not username or name.

## Actual Result

`E007`'s creation fails with `409 Conflict` from the Keycloak Admin
API, because the derived username (`test`) is already taken by
`E006`. The script throws an unhandled exception and stops — `E007`
receives no identity, no department group, and no role assignment.

## Root Cause / Suspected Cause

Username is derived solely from `$employee.FirstName.ToLower()` (see
the existing `TODO (REQ-002)` comment already present in
`provision-users.ps1`, written before this was observed in practice).
This does not guarantee uniqueness. Keycloak enforces username
uniqueness at the platform level, so any two employees sharing a
first name will collide.

## Evidence

```

E007 (test): NOT FOUND - creating...
Exception: ...\KeycloakUsers.ps1:110
Line |
 110 |          throw "Failed to create user '$Username': $($_.Exception.Mess …
     | Failed to create user 'test': Response status code does not
     | indicate success: 409 (Conflict).
```

## Impact

Joiner provisioning fails entirely for the second employee in a
collision — no partial/orphaned identity is created (the failure is
at least clean in that respect), but the employee simply cannot be
onboarded until the collision is resolved. Duplicate first names are
a realistic, common occurrence in any real organization — this is
not a purely theoretical edge case.
